# Architecture

## Overview

One TanStack Start application. Several entry points call one service layer, which talks to PostgreSQL through Prisma. Tools are defined once and served over several transports.

```
Browser UI ──> routes + createServerFn ─────────────┐
REST client ──> /api/v1/* server routes ─────────────┤
MCP client ──> /api/mcp server route ────────────────┼──> src/server/* ──> Prisma ──> PostgreSQL
AI assistant ──> /api/chat (TanStack AI + OpenRouter)┤
                     └── tools from src/tools/ ───────┘
Browser agent ──> WebMCP (document.modelContext) ──> client tools ──> same server functions
Voice ──> SpeechRecognition ──> assistant panel; assistant ──> speechSynthesis
```

## Data model

```
Project     id, name, key (short code like "TOK", unique), description, color, nextTaskNumber, archivedAt, createdAt, updatedAt
Status      id, projectId, name, order, category (todo | in_progress | done)
Task        id, projectId, statusId, number (per project, so TOK-42), title, description,
            priority (none | low | medium | high | urgent), dueDate, order, completedAt,
            createdAt, updatedAt
Subtask     id, taskId, title, done, order
Label       id, projectId, name, color
TaskLabel   taskId, labelId
Comment     id, taskId, body, createdAt, updatedAt
Activity    id, taskId, projectId, type, payload (json), createdAt
```

Task numbers come from `Project.nextTaskNumber`, incremented inside the same transaction that creates the task. Statuses are per project so users can rename or add columns. Every new project gets Backlog, Todo, In progress, Done. `order` fields are floats to allow cheap reorders.

The activity log is append-only and written by the service layer, never directly by a route or tool. The types are listed in `ACTIVITY_TYPES` in `src/server/activity.ts`. So far: `project.created` and `project.archived` from the projects service; `task.created`, `task.updated`, `task.moved`, `task.completed`, and `task.deleted` from the tasks service; `subtask.added`, `subtask.updated`, `subtask.completed`, `subtask.reopened`, `subtask.moved`, and `subtask.deleted` from the subtasks service; and `comment.added`, `comment.updated`, and `comment.deleted` from the comments service. Restoring a project writes no row. A call that changes nothing, such as archiving an archived project or an empty task update, is not a mutation and writes no row either.

`listTaskActivity` in `src/server/activity.ts` reads one task's activity rows (id, type, payload, createdAt), oldest first, and throws `NotFoundError` for an unknown task. Rows that share a `createdAt` are sorted by id only so the result is stable; the id is a random cuid, so their order is arbitrary, not the order they were written. It reads through the task, so the rows of a deleted task, whose `taskId` is now null, are not part of this per-task read; they stay in the project history for a project feed. Only the task page calls it so far. The REST route `GET /tasks/:id/activity` and the MCP and AI tool surfaces for activity wait for F32 and the tool issues (F34 onwards).

`prisma/schema.prisma` adds these rules to the field list. Ids are `cuid(2)` strings. `Project.key` is unique, and so are `(projectId, number)` on Task and `(projectId, name)` on Label. Deleting a Project deletes its statuses, tasks, labels, and activity. Deleting a Task deletes its subtasks, task labels, and comments. A Status that tasks still use cannot be deleted (the foreign key is `RESTRICT`), so a service that removes a status has to move its tasks first. `Activity.taskId` is nullable and set to null when the task is deleted, so the project history keeps the entry. `dueDate` is a PostgreSQL `date`: a calendar day with no time or zone. TaskLabel has `(taskId, labelId)` as its primary key and a separate index on `labelId` for filtering tasks by label.

## Service layer

`src/server/*.ts` exports plain async functions. Each takes the schema's input type (`z.input`), parses it again with the shared Zod schema from `src/schemas/`, and returns plain objects, so a caller that skips validation still gets trimmed strings and an upper-case project key. Invalid input throws a `ZodError`. The services are the only place that touches Prisma. Server functions, REST handlers, MCP tools, and AI tools are thin: parse input with the shared Zod schema, call the service, shape the response.

Services do not leak Prisma error codes. A missing record throws `NotFoundError` (`code: 'not_found'`) and a unique-rule clash, such as a taken project key, throws `ConflictError` (`code: 'conflict'`), both from `src/server/errors.ts`. `NotFoundError` has an optional `entity` naming the missing record (`'project'`, `'task'`, `'status'`, `'label'`, and so on); the tasks service sets it, and `createTaskFn` passes it on so the create task dialog can say which record is gone. The transports map these two classes, and `ZodError`, to their own error shapes. The REST handlers share one mapping, `errorResponse` in `src/lib/rest.ts`, described under REST API.

The projects service creates every project with `DEFAULT_STATUSES` (Backlog, Todo, In progress, Done) and its `project.created` row in one transaction. `listProjects` leaves archived projects out unless `includeArchived` is true. Archiving an archived project and restoring one that is not archived change nothing. The seed imports `DEFAULT_STATUSES` and `ACTIVITY_TYPES` from the services, so demo data and real data cannot drift apart.

The statuses service lists a project's statuses in board order and adds, renames, reorders, and deletes them. `addStatus` appends after the highest `order`; two adds at the same moment can store the same value, which a single-user app accepts. `reorderStatuses` takes every status id of the project in the new order and rewrites `order` as 1..n on each call, so the float `order` holds whole numbers in practice. A list that misses a status or holds one from another project throws `ConflictError`, because the client's view is stale. `deleteStatus` throws `ConflictError` while tasks still use the status, and the `RESTRICT` key backs that check up for a task created in between; the remaining statuses keep their `order` values. A project may lose its last status, and archived projects accept new statuses. Status changes write no activity rows.

The labels service lists a project's labels sorted by name, and creates and deletes them. A label name is unique within its project regardless of case, so "Bug" and "bug" cannot both exist and a screen reader user never meets two labels that sound the same: `createLabel` trims the name, throws `ConflictError` when the project has a label of that name in any case, and throws `NotFoundError` for an unknown project. The service compares the names as plain text, so `_` and `%` match only themselves. The database index is case-sensitive, so the service check is the rule. The colour must be one of `PROJECT_COLORS` and is stored in lower case. Only `createLabel` checks it, so a label written another way can hold a colour outside the palette; the seed's label colours are all on it, which `src/server/seed.test.ts` checks. `deleteLabel` returns the deleted label; its TaskLabel rows go with it, so its tasks lose the label and nothing else. Label changes write no activity rows.

The tasks service creates, reads, lists, updates, moves, completes, and deletes tasks. `createTask` takes the number from `Project.nextTaskNumber` with one atomic increment at the start of its transaction. The increment row-locks the project, so concurrent creates in one project queue there and each gets its own number under PostgreSQL's default read committed level; the transaction allows 10 seconds to start and to finish, because a burst of creates holds a pooled connection each while it waits. Numbers are never reused, not even after a delete. Without a `statusId` the task goes to the end of the project's first status; a project with no statuses throws `ConflictError`. Due dates are `YYYY-MM-DD` strings going in and coming out of the service, so the UI, REST, and tools all see one shape with no time-zone shift; inside, they are UTC midnight `Date`s in Prisma, which the `date` column stores as that day. `listTasks` returns the project's tasks in board order (status order, then status id, then task order, then number, so ties come back the same way every time) and filters by status, priority, label, due range (both ends included), completed (`false` keeps tasks with no `completedAt`, `true` only those with one), and text, which matches title or description ignoring case; only the filters given apply. Every task comes back with its `status` and a flat `labels` array.

`updateTask` changes title, description, priority, and due date; `null` clears the description or due date. `moveTask` takes a destination status, an index, or both. The index counts the destination's other tasks, so the moving task is left out of its own column; an index past the end means the end. Without an index the task goes to the end of another status, and stays where it is when the status is its current one: no `order` or `completedAt` change and no `task.moved` row, so a client that sends back a whole edit form with the unchanged status only gets the field update. The new `order` is the midpoint of its neighbours, one less than the first, or one more than the last, which costs one update. When repeated moves leave no float between two neighbours, the column is rewritten as 1..n first. `completedAt` follows the status category: a task created in or moved into a done-category status gets one (a move inside Done keeps the old value), moving to a status that is not done clears it, and a reorder within one status keeps it as it is, so a task completed in a project with no done-category status stays completed when it is reordered. `completeTask` sets `completedAt` and moves the task to the end of the project's first done-category status; a task already in one, or in a project without one, stays where it is. A task created in or moved into a done-category status gets `completedAt` but writes `task.created` or `task.moved`, not `task.completed`; only `completeTask` writes `task.completed`, so a count of completions has to read `completedAt` rather than the activity types. `deleteTask` writes `task.deleted` before the delete, and the foreign key then sets `taskId` to null on that row and the task's older rows, so the project history keeps them. When a task is deleted between the read and the write of `updateTask`, `moveTask`, or `completeTask`, Prisma's P2025 becomes the task's `NotFoundError`.

Each task mutation writes one activity row in its transaction: `task.created` with `{ number, title }`, `task.updated` with `{ number, fields }` naming the fields that changed, `task.moved` with `{ number, from, to }` status names (equal for a reorder in one column), `task.completed` with `{ number }`, and `task.deleted` with `{ number, title }`. A call that changes nothing writes no row: an update whose values equal the current ones, a move that leaves the task in place (its own position, or past the end when it is already last), and completing a completed task.

The subtasks service lists, adds, updates, moves, and deletes a task's subtasks. `listSubtasks` returns them top to bottom (`order`, then id so ties come back the same way). `addSubtask` trims the title (1 to 200 characters) and appends after the highest `order`, not done. `updateSubtask` takes a title, `done`, or both, and compares the trimmed title with the stored one, so sending the current values back changes nothing. `moveSubtask` takes an index among the task's other subtasks, so 0 is the top and an index past the end means the end, and rewrites the task's subtasks as 1..n, as `reorderStatuses` does, rather than taking the midpoint as `moveTask` does: a task has few subtasks, and whole numbers never run out of room between two neighbours. `deleteSubtask` returns the deleted subtask and leaves the others' `order` as it was. The schemas in `src/schemas/subtask.ts` are strict, so an unknown key is a `ZodError`. An unknown task (`listSubtasks`, `addSubtask`) or subtask (the rest) throws `NotFoundError`. `deleteTask` deletes the task's subtasks with it, and `getTask` and `listTasks` do not return subtasks.

Subtask mutations on one task run one at a time. The UI, REST, MCP and the assistant can all write at once, so every mutation (add, update, move, delete) first locks the task's row with `SELECT … FOR UPDATE` inside its transaction, as `createTask` locks the project with its increment, and reads the subtask again under the lock. Two adds then get distinct orders, two moves each start from the order the other committed so the task keeps 1..n, and a write that waited on `deleteTask` finds the task gone and throws `NotFoundError` rather than deadlocking on the cascade. The writers queue on the row while holding a pooled connection, so these transactions get `createTask`'s 10 second `maxWait` and `timeout`.

Each subtask mutation writes one activity row in its transaction, with the task's `projectId` and `taskId`, so it shows in `listTaskActivity`. Every payload has the task's `number` and the subtask's `title`, its new title after a rename: `subtask.added`; `subtask.completed` and `subtask.reopened` when `done` is the only change; `subtask.updated` with `fields` (`title`, and `done` when both changed in one call, with the new `done` beside it so the sentence reads "Renamed and completed" or "Renamed and reopened") for anything else; `subtask.moved` with `from` and `to`, the old and new index, which the sentence counts from 1 ("Moved the subtask “X” from position 4 to 1."); and `subtask.deleted`. The seed's `subtask.added` rows have only the title, so the payload schema keeps `number` optional. A call that changes nothing writes no row: an empty update, an update with the current values, and a move to the subtask's own place (or past the end when it is already last).

The comments service lists, adds, updates, and deletes a task's comments. `listComments` returns them oldest first (`createdAt`, then id, so comments of one millisecond come back the same way each time, though not in write order). `addComment` and `updateComment` trim the body, which must then be 1 to 10000 characters, and `updateComment` compares the trimmed body with the stored one, trimmed as well, so sending the current body back changes nothing and returns the comment as it is. `deleteComment` returns the deleted comment. The schemas in `src/schemas/comment.ts` are strict, so an unknown key is a `ZodError`, and an update must give the body, its only field. An unknown task (`listComments`, `addComment`) or comment (the rest) throws `NotFoundError`. Each mutation locks the task's row first and reads the comment again under the lock, with the same 10 second `maxWait` and `timeout`, as the subtasks service does, so a write that waited on `deleteTask` throws `NotFoundError`. `deleteTask` deletes the task's comments with it, and `getTask` and `listTasks` do not return comments.

Each comment mutation writes one activity row in its transaction, with the task's `projectId` and `taskId`: `comment.added`, `comment.updated`, and `comment.deleted`. A row records that a comment was added, edited, or deleted, and which one: the payload is `{ number, commentId }`. It never holds the comment's text, so a deleted comment's words are gone from the log too, and an edit leaves no copy of the old body. The seed writes the same payload for its `comment.added` rows. The Activity section reads them as "Added a comment", "Edited a comment", and "Deleted a comment". Rows written before this change hold `{ body }` or `{ number, excerpt }`; every field of the comment payload schemas is optional, so they still parse and read as the same sentences, which never quote a body or excerpt a row still carries. An update with the current body writes no row.

The dashboard service has three reads. `listDashboardTasks(today)` takes today as a `YYYY-MM-DD` string, which the caller picks so the server render and the browser agree on the day, and returns `{ dueToday, overdue }` across unarchived projects. It is one query, not one per project: tasks with no `completedAt`, a due date on or before today, and a project whose `archivedAt` is null. Today goes through the tasks service's exported `toCalendarDate`, so it is compared as the same UTC midnight the `date` column stores. Due today means due on that day; overdue means due before it and not completed, the rule the board's Overdue word, the overdue filter and REST use, so a completed task is in neither list. Tasks come back ordered by due date, then project name, then project key, then number (project names repeat and every project numbers from 1, so the key keeps the order stable), each with its `status`, flat `labels` and `project` (`id`, `name`, `key`). `listRecentActivity(limit = RECENT_ACTIVITY_LIMIT)` returns the latest 20 activity rows whose project's `archivedAt` is null, newest first (then by id, so rows written in the same millisecond keep one order), each with `id`, `type`, `payload`, `createdAt`, `project` (`id`, `name`, `key`) and `task` (`id`, `number`), which is null for a project row and once the task is deleted, since the column is set to null. `listProjectProgress()` returns every unarchived project, ordered by name, then key, as `{ id, name, key, total, done }`. It runs two operations and joins them in memory: the projects, then `task.groupBy` over those projects' tasks, which counts all of them (`total`) and those with `completedAt` set (`done`, so a task created in a Done status counts) in one statement, so `done` is never more than `total`. Neither read makes a call per project: Prisma loads a nested relation with one statement per table, never per row, so the number of Prisma calls and statements is fixed, and a unit test spies on the Prisma calls and compares one project with five.

The search service has one read. `search(query, options?)` parses `{ query, ...options }` with the strict `searchSchema` from `src/schemas/search.ts`: the query is trimmed and must be 1 to 200 characters, and `limit`, the most results of each kind, is 1 to 50 and defaults to 10. It returns `{ projects, tasks }` from unarchived projects only: projects whose name or key contains the query, as `{ id, name, key, color }`, and tasks whose title or description contains it, as `{ id, number, title, project: { key, name }, status: { name } }`. Completed tasks are included. Matching ignores case through Prisma's `contains` and `startsWith` with `mode: 'insensitive'`, which become an unescaped ILIKE, so the service puts a backslash before each `\`, `%` and `_` in the query; the backslash is PostgreSQL's default LIKE escape, so those characters match only themselves and a trailing backslash does not fail the query. A task reference is matched exactly, never as text: a query shaped like `KEY-N` (a letter, 1 to 9 more letters or digits, a dash, digits, in any case) also finds the task with that project key, upper-cased, and that number, so `tok-1` finds TOK-1 and not TOK-10, and `TOK` or `OK-1` match no reference. A number too big for the column is not a reference. Within each kind, names or titles that start with the query, the project whose key is the query, and the referenced task come first, then the other matches, each group most recently updated first (then by id). Each kind is two reads: the first takes that starts-with group up to the limit; when it comes back short, the second takes the other matches with `NOT` the same group-1 condition for the room left, so a task that matches by reference and by description, or a project that matches by name and key, comes back once. Keys are stored in upper case, so the key match compares the upper-cased query exactly; an insensitive `equals` would be another ILIKE. The two kinds are read at the same time. The `search` tool (F34) calls it, and so does `searchFn` (`src/fns/search.ts`), a GET server function that validates with `searchSchema` and serves the command palette (F66). REST search is F32.

`createTask` and `updateTask` take `labelIds`. On create the labels are attached in the task's transaction. On update `labelIds` is the whole new set, in any order, and `[]` clears it: the service compares it with the current labels, writes only the difference as a `deleteMany` and a `create` on the task's one update statement, and names `labels` in the `task.updated` fields. A set equal to the current one writes nothing. Both throw `NotFoundError` for a label outside the task's project and write nothing. A label deleted between that check and the write trips the TaskLabel foreign key (P2003), which becomes the same `NotFoundError`; on create, a status deleted the same way trips the Task foreign key and becomes the status's `NotFoundError`. The service tells the two apart by the constraint name in the error. A repeated id, or more than 50 ids, is a Zod error.

## Web UI

- Routes load data with `loader` plus TanStack Query for client cache and invalidation.
- Mutations go through `createServerFn({ method: 'POST' })` wrappers in `src/fns/`, called from TanStack Query mutations with optimistic updates for local changes (checkbox, status move).
- A server function validates its input with the shared schema through `.inputValidator(schema)`. An error class thrown on the server reaches the client as a plain `Error` without its class or `code`, so an expected service error that a form shows on a field comes back as a value instead: `createProjectFn` returns `{ ok: true, project }` or `{ ok: false, code: 'conflict', message }`. Any other error is thrown, and the form shows a generic message. A `NotFoundError` in a route's server function becomes the router's `notFound()`.
- The sidebar's project list is the `projectsQueryOptions()` query (key `['projects']`). The `_app` loader fills it with `ensureQueryData`, so the list is in the server HTML, and the sidebar reads it with `useSuspenseQuery`. After a create the sidebar adds the project to that cache with `setQueryData` and refetches it in the background. There is no `router.invalidate()`: the loader would only read the same cache.
- The dashboard (`_app/index.tsx`, the index route) shows what needs attention. Its loader computes `today` with `toCalendarDay`, and `now` (an ISO string, the moment the activity's relative times count from) and returns `{ today, now }`, as the board and the task page do, so the server render and hydration use the same day and the same words. It fills `dashboardQueryOptions(today)` (key `['dashboard', today]`), `recentActivityQueryOptions()` and `projectProgressQueryOptions()` together with `ensureQueryData` and `revalidateIfStale: true`; nothing invalidates the dashboard keys, so cached data shows at once and, with the default `staleTime` of 0, is refetched in the background on every visit, which is how the progress and the activity catch up after a task is completed elsewhere in the app. The page reads the same keys with `useSuspenseQuery`. ## REST API

Base path `/api/v1`, implemented as TanStack Start server routes (`createFileRoute` with `server.handlers`). JSON in and out. No auth. Errors return `{ error: { code, message, issues? } }`.

A handler parses the query or body with the shared Zod schema, calls the service, and returns `Response.json`. Its body runs inside `handle()` from `src/lib/rest.ts`, which turns a thrown error into the envelope:

| Thrown                                                               | Status | `code`                                                                  |
| -------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------- |
| `ZodError`                                                           | 400    | `validation`, with the Zod `issues` (each has a `path` and a `message`) |
| Body that is not JSON (`readJsonBody`)                               | 400    | `invalid_json`                                                          |
| Body whose `Content-Type` is not `application/json` (`readJsonBody`) | 415    | `unsupported_media_type`                                                |
| Body over `readJsonBody`'s `maxBytes` (`PayloadTooLargeError`)       | 413    | `payload_too_large`                                                     |
| `InvalidChatRequestError` (`/api/chat` body that is not AG-UI)       | 400    | `validation`, without issues                                            |
| `NotFoundError`                                                      | 404    | `not_found`                                                             |
| `ConflictError`                                                      | 409    | `conflict`                                                              |
| anything else                                                        | 500    | `internal`; the error is logged and its message is not sent             |

POST and PATCH must send `Content-Type: application/json` (a `charset` parameter is fine). Without it, a page on another site could post a `text/plain` body with `mode: 'no-cors'`, which the browser sends without a CORS preflight. Requiring JSON forces the preflight, which fails because the API sends no CORS headers.

A success returns the bare resource or array, not a wrapper. Create returns 201, everything else 200. `GET /projects` leaves archived projects out unless the query has `includeArchived=true` (`listProjectsQuerySchema`, a `z.stringbool()` that also reads `1`/`0` and `yes`/`no`; any other value is a 400). `DELETE /projects/:id` archives and returns the archived project; a second DELETE returns it unchanged. Start runs only the handlers of the deepest matching route, so `/projects/:id` does not inherit the GET and POST of `/projects`. Status writes, restoring a project, and completing a task as its own call are not on REST yet.

`GET /projects/:id/tasks` takes F23's filter names (`listTasksQuerySchema`): `status`, `priority`, `label`, `due` and `q`. A query parameter given twice keeps its last value, because the handler reads the query with `Object.fromEntries`. An empty value means the filter is absent for all five names, because an HTML GET form or the filter bar sends `?priority=` for a filter nobody picked; a value the filter does not accept, such as `due=soon`, is a 400. The query schema is strict: an unknown parameter, such as `statusId`, `completed` or `dueFrom`, is a 400 rather than an unfiltered list. `dueFilterRange` in `src/lib/dates.ts` turns `due` into the service's range, counted from today, the server's local calendar day (the app is local, so it shares the browser's zone): `today` is that day, `week` is today and the six days after it, and `overdue` is due before today and not completed (`completed: false`). Overdue means that on every surface, the board card's Overdue mark and the API alike, so a task due yesterday in a done status is not overdue.

`PATCH /tasks/:id` takes the update fields, `labelIds` among them, and the move fields (`statusId`, `index`) in one body (`patchTaskSchema`), parsed once, so any invalid field is a 400 before anything is written. The task schemas, `patchTaskSchema` and `createTaskSchema`, are strict: an unknown key is a 400 with an `unrecognized_keys` issue, so `{ "status": "…" }` (the list filter's name, not the field's) cannot return 200 with nothing changed. The handler calls `moveTask` first when the body has `statusId` or `index`, then `updateTask` when it has a field, and returns the last result; an empty body returns the task unchanged. The move goes first, so a status outside the project is a 404 that changes nothing and writes no activity. A label outside the project is a 404 from the update, which runs after the move, so a body that both moves the task and names such a label keeps the move; F56's `patchTask` puts both in one transaction. The two writes are separate transactions: a task deleted between them gets the move but not the update, and the client sees 404. `DELETE /tasks/:id` deletes the task for real and returns it; its activity rows, the `task.deleted` row included, stay in the project history, and a second DELETE is a 404.

```

POST   /projects                 create
GET    /projects/:id             with statuses
PATCH  /projects/:id
```

The OpenAPI document is generated from the Zod schemas and served at `/api/v1/openapi.json`, with a rendered page at `/api-docs`.

## Tools: one definition, four consumers

`src/tools/definitions.ts` declares each tool with TanStack AI's `toolDefinition({ name, description, inputSchema, outputSchema })`, and the write tools that archive or delete add `needsApproval: true` (see the paragraph on approval below). `src/tools/server.ts` turns each definition into a server tool with `.server(execute)` and exports them all as `serverTools`, the list the MCP server and the assistant take. It also exports `readServerTools`, the eight read tools (`list_projects`, `get_project`, `list_tasks`, `get_task`, `search`, `list_subtasks`, `list_labels`, `list_comments`), which the MCP server marks `readOnlyHint: true`.

- The description is written for a model: what the tool returns, when to use it rather than another tool, and what each filter means.
- Input schemas come from `src/schemas/` and are strict, so a key the tool does not take, such as REST's `status` sent to `list_tasks`, is a validation error rather than a filter silently dropped.
- TanStack AI, MCP and WebMCP turn the input schema into JSON Schema. TanStack AI (through `~standard.jsonSchema.input()`) and the MCP SDK convert in `z.toJSONSchema`'s input mode, which describes a transform's input side and does not throw; a defaulted field such as `limit` comes out optional with its default. The default output mode throws on a transform and lists defaulted fields as required. The tool input schemas have no transforms, so they convert in both modes: `listTasksToolSchema` sits beside `listTasksSchema` with `q` as a plain trimmed string, and the service still parses with its own schema. The write tools take the id the service takes as its first argument beside the service schema's fields: `createTaskToolSchema` (`projectId` and `createTaskSchema`'s fields), `updateTaskToolSchema` (`taskId` and `updateTaskSchema`'s), `moveTaskToolSchema` (`taskId` and the move fields, with `moveTaskSchema`'s "Give a status, an index, or both." refine) and `taskIdToolSchema` (`taskId` alone, also for `list_subtasks` and `list_comments`). `projectIdToolSchema` in `src/schemas/project.ts` is `projectId` alone, for `get_project`, `archive_project` and `list_labels`. `create_project` takes `createProjectSchema.strict()`. The subtask, label and comment tools follow the same rule: `addSubtaskToolSchema` (`taskId` and `createSubtaskSchema`'s fields), `updateSubtaskToolSchema` and `moveSubtaskToolSchema` (`subtaskId` and `updateSubtaskSchema`'s or `moveSubtaskSchema`'s fields) and `subtaskIdToolSchema` in `src/schemas/subtask.ts`; `createLabelToolSchema` (`projectId` and `createLabelSchema`'s fields) in `src/schemas/label.ts`; and `addCommentToolSchema` (`taskId` and the body), `updateCommentToolSchema` (`commentId` and the body) and `commentIdToolSchema` in `src/schemas/comment.ts`. Every id argument uses `projectIdFieldSchema`, `taskIdFieldSchema`, `subtaskIdFieldSchema` or `commentIdFieldSchema`, which carry the description the model reads. A test converts every definition's input and output schema in both modes.
- Output schemas describe the JSON a tool returns: ISO strings for timestamps and `YYYY-MM-DD` for due dates. Each is an object, because MCP's `structuredContent` and `outputSchema` must be one, so a list comes wrapped: `list_projects` returns `{ projects }`, `list_tasks` `{ tasks }`, `list_subtasks` `{ subtasks }`, `list_labels` `{ labels }` and `list_comments` `{ comments }`. They live in `src/schemas/` beside the input schemas (`projectOutputSchema`, `taskOutputSchema`, `subtaskOutputSchema`, `labelOutputSchema`, `commentOutputSchema`, `searchResultsOutputSchema`, and so on). The write tools reuse them: `create_project` and `archive_project` return `projectWithStatusesOutputSchema`, the task tools return `taskOutputSchema`, and the subtask, label and comment tools return the one row they wrote or deleted with `subtaskOutputSchema`, `labelOutputSchema` or `commentOutputSchema`. The chat engine parses every result with the output schema.
- Every `execute` is built by `serve(definition, call)` in `src/tools/server.ts`, and `call` makes one service call; it only splits the id from the other arguments. `call`'s return type is the output schema's input type with a `Date` allowed wherever the schema has a string. Typecheck therefore catches a service whose field names, nullability or nesting drift from the tool's output schema, but not string formats: a due date returned as a `Date` passes typecheck and fails the output schema at runtime. `serve` parses the arguments with the definition's input schema, as the chat engine does before it calls a tool, so a direct call (MCP, a test) gets the same defaults and trimming. It sends the service result through JSON, so Dates become ISO strings, and maps errors with `toToolError` from `src/tools/errors.ts`, as `handle()` and `errorResponse` do for REST: a `NotFoundError` or `ConflictError` becomes a `ToolError` with the same code (`not_found`, `conflict`) and message, and a `ZodError` becomes a `ToolError` with code `validation` and a message from `z.prettifyError`, one line per issue followed by its path (`✖ Search text is required.` then `→ at query`), never the issues array. Any other error, such as a Prisma error, is logged on the server with `console.error` and becomes a `ToolError` with code `internal` and the message "Something went wrong on the server.", so database details never reach the model provider or an MCP client. The chat engine puts a thrown error's message in the tool result, so the model reads it and can correct its call. The chat engine also parses the arguments with the input schema before it calls `execute`, and rejects invalid ones with its own message ("Input validation failed for tool ..."); the MCP SDK does the same for a tool registered with an input schema. The prettified `ToolError` message therefore reaches a direct caller (a test, the MCP server, which calls `execute` itself) and any error the service raises, while model input the engine rejects first gets the engine's message.

Consumers:

1. AI assistant. `/api/chat` calls `chat({ adapter: openRouterText(model), messages, tools: assistantTools })` and streams with `toServerSentEventsResponse`. Data tools use `.server()` implementations; `chat()` runs them on the server and streams each call and its result to the panel. `assistantTools` (`src/tools/server.ts`) is `serverTools` without the four `needsApproval` tools: with no Approve and Deny prompt, such a call would pause the run with nothing to answer it. F40 adds the prompt and drops the filter. UI tools are passed as definitions and executed in the browser through `useChat({ tools })` with `.client()` implementations.
2. MCP server. `createMcpServer()` in `src/tools/mcp.ts` registers each of the 23 tools in `serverTools` on an `McpServer` from `@modelcontextprotocol/sdk` with the definition's description, input schema and output schema. The handler calls the tool's `execute` and returns the result twice, as `structuredContent` and as JSON text; an error goes through `toToolError`, which returns a `ToolError` as it is and maps any other error, and becomes an `isError` result whose text is the code and message (`not_found: No project with id p1.`), so an unexpected error reaches the client as the generic `internal` message. The tools in `readServerTools` carry the annotations `readOnlyHint: true` and `openWorldHint: false`; every other tool carries `readOnlyHint: false` and `openWorldHint: false`, with `destructiveHint: false` on the five that only add a row (`create_project`, `create_task`, `add_subtask`, `create_label`, `add_comment`) and `destructiveHint: true` on the write tools that overwrite, clear, move or remove data. `destructiveHint` is separate from `needsApproval`, which alone decides who takes `confirm`. For the four tools whose served object has `needsApproval: true`, and only on this transport, the input schema is the definition's strict schema extended with an optional boolean `confirm`, and the description gains a sentence asking for `confirm: true` once the user has approved. Without `confirm: true` the handler returns an `isError` result with the code `confirmation_required` (`confirmation_required: delete_task needs the user's approval. Ask the user, then call it again with confirm: true.`) and calls nothing; with it, the handler drops `confirm` and calls `execute` with the rest. `confirm` is optional rather than `z.literal(true)` so a missing value gets that refusal instead of the SDK's generic input error. The SDK skips the output schema check for an `isError` result, so the refusal needs no `structuredContent`. `connectMcpServer(transport)` connects a new server and reads a `tools/call` without `arguments` as `{}`, which the spec allows and the SDK's strict input check would otherwise refuse. The SDK checks the arguments against the input schema before the handler runs, and reports a failure, such as an unknown key, as an `isError` result too. The route `src/routes/api/mcp.ts` serves it over Streamable HTTP at `/api/mcp` and is stateless: each POST builds a new server and a `WebStandardStreamableHTTPServerTransport` with no session id generator and JSON responses, and closes the server, which closes the transport, once the response is ready, so nothing outlives the request. A POST whose `Host` header is not `localhost`, `127.0.0.1` or `[::1]` (any port) gets a 403 JSON-RPC error before any of that, so a DNS-rebinding page cannot read the data through the browser; without a `Host` header, as in Vitest, the request URL's host is checked. GET and DELETE answer 405 with a JSON-RPC error, as the SDK's stateless examples do. The server also registers two resource templates, `project://{id}` and `task://{id}` (no list callback, so `resources/list` is empty), and the `daily_review` prompt. A resource read calls the same services as the tools (`getProject`, `listTasks` and `listLabels`; `getTask`, then `getProject`, `listSubtasks` and `listComments`) and returns `text/markdown` from the pure functions in `src/tools/resources.ts`, which put titles and names on one line and move the headings of descriptions and comments below their section, so user text cannot add a section or a task line. The prompt parses its optional `today` with `dueDateSchema`, defaults to `toCalendarDay(new Date())`, calls `listDashboardTasks`, and returns one user message from `dailyReviewText` in `src/tools/prompts.ts`, which caps each section at 15 tasks. Resources and prompts have no `isError` result, so their errors are JSON-RPC errors: a `ToolError`, `NotFoundError`, `ConflictError` or `ZodError` goes through `toToolError` and becomes `InvalidParams` with the code-prefixed text a tool returns, and anything else is logged by `toToolError` and becomes `InternalError` with the generic `internal` message. `connectMcpServer` reads a `prompts/get` without `arguments` as `{}` too, since the SDK parses the prompt's argument object as given. `docs/mcp.md` says how to add the server to Claude Code.
3. WebMCP. `src/tools/webmcp.ts` runs on the client, feature-detects `modelContext`, and calls `registerTool` for every tool with a JSON Schema derived from the Zod input schema. Data tools execute by calling the server functions; UI tools call the same client implementations as the assistant. Registration uses an `AbortSignal` tied to the shell's lifetime.
4. REST. Not tool-based, but the handlers use the same Zod schemas.

`archive_project`, `delete_task`, `delete_subtask` and `delete_comment` carry `needsApproval: true`, and a test asserts that they are the only tools that do. Until F40 the assistant is not offered them at all (`assistantTools`); F40's Approve and Deny prompt in the panel will ask for confirmation before they execute. Over MCP (F36) they take `confirm: true` and return a `confirmation_required` error result otherwise; WebMCP does the same, and the UI shows the same confirmation dialog when WebMCP triggers them.

Below `md` that button is `display: none` until the shell is shown again, and Radix's `onCloseAutoFocus` runs before that render, so the panel prevents it and moves focus in an effect that runs when `open` turns false, after the commit that shows the shell.
- `useChat({ connection: newestMessagesOnly(fetchServerSentEvents('/api/chat')) })` lives in `AssistantPanel`, which stays mounted while closed, and not in the Sheet content, which Radix unmounts while closed. `newestMessagesOnly` wraps the connection's `connect` so a request carries at most the newest 100 messages (`MAX_CHAT_MESSAGES`), which keeps a long conversation under the 1 MiB body limit; the server trims to the same number anyway. It also passes them through `withAnsweredToolCalls` (`src/lib/tool-call.ts`), which drops a tool call with no output or result, as Stop leaves behind, a result whose call is not in the message, and a reply left with no parts, since the model provider refuses a tool call that no result answers. Slicing whole messages cannot split a call from its result: both are parts of the same assistant message, which the client sends as an assistant message with `toolCalls` (and no `content` when it had no text) followed by a `tool` message per result. The conversation survives a close and reopen, and a reply still streaming when the panel closes runs on and is announced when it ends. The message list is an `ol` labelled by a visually hidden h3 "Conversation"; each item names who wrote it ("You", "Assistant") and renders the message's parts in order in a `max-w-prose` box: consecutive text parts as one `Markdown` block, and each `tool-call` part as a `ToolCallCard` (`src/components/app/tool-call-card.tsx`). `tool-result` parts are not shown on their own, as the engine copies the output onto the tool call. The card is a `role="group"` named "Tool call: List tasks" and shows the tool's name in plain words, its status as text beside a decorative icon, and once done a one-line summary, never the result itself. `src/lib/tool-call.ts` holds the rules. Status: Failed when the call is in the `error` state or its output is chat()'s error shape, `{ error: message }` (or a string starting "Error executing tool:"), and the card then shows that message; Done once it has output; Needs approval in `approval-requested` (for F40); otherwise Running while that reply is loading and Stopped after, as when Stop ends a reply while a tool runs. Summary: a list output is counted ("2 tasks", "1 comment"), a search counts both lists ("1 project and 2 tasks"), a single item (a task with its `labels` or a project with its `statuses` is a single item, not a list) is its title, name or text cut to 60 characters, and anything else is "Done". The card uses the border, foreground and destructive tokens already in the theme, and the running icon spins only with `motion-safe`. A new message, or a new part in the last one, scrolls into view with `block: 'nearest'`. While a reply streams the list follows it only if it was already scrolled to the end, so a user rereading an earlier message is not pulled down. The composer is a form with a visible "Message" label on a `Textarea` (Enter sends, Shift+Enter starts a new line, empty text is not sent), a Send button, and, only while a reply streams, a Stop button that calls `stop()`. Send uses `aria-disabled` rather than `disabled` while a reply streams, so it keeps focus. A finished reply is announced once through `useAnnounce()` ("Assistant: …", or for a reply with no text its tools, "Assistant used List tasks: 2 tasks"), a stop announces "Reply stopped", and an error shows "Could not get a reply. Try again." under the list and announces it. When the server refused the request with 400 or 413 (the error message from `fetchServerSentEvents` reads "HTTP error! status: 413 …"), it says "The conversation is too long to send. Clear the conversation and try again." instead. A message over 20,000 characters (`MAX_CHAT_MESSAGE_LENGTH`) is not sent: it stays in the field, which gets `aria-invalid`, and "Messages can be up to 20,000 characters." shows under the field, joins its `aria-describedby` and is announced; the next edit clears it. The field grows with its text up to `max-h-48` and then scrolls, so a long message never pushes the list out of the panel. A "Clear conversation" button beside Send calls `clear()` from `useChat`, which also cancels a streaming reply and ignores its late chunks (calling `stop()` first would defeat that), announces "Conversation cleared" and keeps focus; it uses `aria-disabled` while the list is empty, so it never disappears under focus. When a reply ends and focus is on the body because Stop had it or was just pressed, focus moves to the Message field. Focus anywhere else stays put, even on the body after a click on plain text beside the panel, so a reply ending never pulls focus into the panel (3.2.5).
- `/api/chat` (`src/routes/api/chat.ts`) first checks the `Host` header with `isLoopbackHost` from `src/lib/loopback.ts`, the check `/api/mcp` uses, and answers 403 `forbidden` unless it names `localhost`, `127.0.0.1` or `[::1]` on any port, so a page that rebinds its own domain to 127.0.0.1 is refused before the body is read or the key is used. It then reads the body with `readJsonBody` from `src/lib/rest.ts`, so anything but `application/json` gets 415 `unsupported_media_type` and another site cannot spend the key through a cross-site `text/plain` POST, which needs no CORS preflight. `readJsonBody(request, { maxBytes: MAX_CHAT_BODY_BYTES })` answers 413 `payload_too_large` for a body over 1 MiB before parsing it: by the `Content-Length` header before anything is read, otherwise by the UTF-8 length of the text. Without the header, as with a chunked body, the whole body is buffered before it is measured, so the limit bounds what is parsed, not what is held in memory. `parseChatRequest` (`src/server/assistant.ts`) first checks the AG-UI shape with `chatParamsFromRequestBody` (400 `validation` through `InvalidChatRequestError`, which `errorResponse` maps), which also drops TanStack's inbound `parts`. `trimChatHistory` keeps only `user`, `assistant` and `tool` messages, so a client cannot put a `system` or `developer` message beside the system prompt, keeps the newest 100 (`MAX_CHAT_MESSAGES`), and drops everything left before the first user message, as some models refuse a history that does not open with the user. `pairToolMessages` then drops a `tool` message whose call is not in an earlier kept assistant message, and a tool call that no later `tool` message answers; an assistant message left with neither text nor tool calls goes too. One message on the client becomes several on the wire, so this trim can cut a call from its result even though the client's cannot. When no user message is left, the request is refused with 400 `validation` ("The request has no user message.") and `chat()` is never called. The size caps run on that kept history only, so an old reply or a system message the trim drops cannot refuse the request: each kept text, string `content` or the `text` of a content part, may be at most 100,000 characters (`MAX_CHAT_PART_LENGTH`, 400 `validation` with the issues), so a long assistant reply still goes through. Only the newest user message is held to 20,000 characters (`MAX_CHAT_MESSAGE_LENGTH`, 400 `validation`); older messages, user ones included, are limited by the part cap alone. It is found after the role filter, so a trailing assistant or system message cannot turn a long user message into older history. The limits live in `src/lib/assistant.ts`, which imports no server code, so the panel uses the same numbers. `startAssistantReply` builds `createOpenRouterText(OPENROUTER_MODEL, OPENROUTER_API_KEY, { appTitle: 'todoOverKill' })` and starts `chat({ adapter, messages, threadId, runId, systemPrompts: [ASSISTANT_SYSTEM_PROMPT], tools: assistantTools, abortController })`, or returns null without a key; the route streams the result with `toServerSentEventsResponse`. A tool's result reaches the client as `TOOL_CALL_RESULT` with the result as JSON `content`; a tool that throws a `ToolError` sends `{ "error": message }` with `metadata.tanstack.state: 'output-error'`. Errors use the REST envelope through `errorJson` and `handle`. The system prompt (`src/server/assistant.ts`) asks for plain language and short replies (3.1.5), says the assistant can read and change projects, tasks, subtasks, labels and comments with its tools and should answer from real data, asks it to say in plain words what it changed, and says it cannot archive or delete anything yet. Stop aborts the browser's fetch, which aborts the request; `startAssistantReply` forwards `request.signal` to the controller, which ends the model call and the stream, and starts it aborted if the request was aborted while its body was read.

Missing key: `getAssistantStatus()` reports `enabled: false` (only whether the key is set leaves the server, never the key), the `_app` loader fills `assistantStatusQueryOptions()` so the panel never suspends, the panel explains that the assistant is off and how to turn it on and shows no composer, `/api/chat` answers 503 with code `assistant_disabled`, and the voice button is hidden. ## Repository rules

The `main` branch has a GitHub ruleset. Changes reach `main` only through a pull request, every review conversation must be resolved, the CI job "Lint, typecheck, unit, and e2e" must pass on a branch that is up to date with `main`, and force pushes and deletion are blocked. ## Local infrastructure

`docker-compose.yml` starts PostgreSQL on port 5434, bound to 127.0.0.1 only (5432 and 5433 are already in use on the development machine). `.env.example` documents `DATABASE_URL`, `OPENROUTER_API_KEY`, and `OPENROUTER_MODEL`. Environment variables are validated with `t3env`. The schema also has an optional `DATABASE_URL_TEST`, which only the test runs set, to their own container. The compose database is for development only; a volume created before the tests moved to containers still holds an unused `todo_over_kill_test` database.

The schema in `src/env.ts` reads `process.env`, because server variables have no `VITE_` prefix and never reach `import.meta.env`. It validates the raw strings and passes them through unchanged, so `env` and `process.env` (which Prisma reads) hold the same values. t3-env treats the module as client code whenever `window` exists and blocks server variables there, so unit tests of server code need the `// @vitest-environment node` docblock.

The config function in `vite.config.ts` loads `.env` into `process.env` with `src/lib/load-dot-env.ts` before any plugin hook runs. Variables already set in the shell take precedence. The loader drops the keys it loaded before, so a key deleted from `.env` does not survive a dev server restart. TanStack Start's load-env plugin copies `.env` again later, which changes nothing because every key already holds the value it would write. For the dev and preview servers the config function then imports the schema, so a missing or invalid variable stops startup with a readable message. When a restart after a `.env` edit fails validation, `process.env` goes back to its previous values, Vite logs the message and "server restart failed", and the old server keeps running with its old environment. `vite build` does not evaluate the schema and runs without a `.env`.

`src/server.ts`, the custom server entry, imports the schema first, so `dist/server/server.js` fails when it loads rather than on the first request. It does not read `.env`: outside `pnpm preview` the variables come from the real environment, for example `node --env-file=.env`.

`prisma.config.ts` loads `.env` with the same loader, so shell variables win there too. It passes `DATABASE_URL` to Prisma only when the variable is set. Without it `prisma generate` still runs, which is why `postinstall` can call it on a fresh clone, and the commands that need a database fail with Prisma's own message. Prisma's `env()` helper is not used because it throws while the config loads. The generated client goes to the gitignored `src/generated/prisma`. Since Prisma 7, `prisma migrate dev` does not regenerate it, so `pnpm db:generate` has to run after every schema change. `src/server/db.ts` builds the client on `@prisma/adapter-pg` and connects to `DATABASE_URL_TEST` when `NODE_ENV` is `test` (Vitest sets it) and to `DATABASE_URL` otherwise. Under `NODE_ENV=test` without `DATABASE_URL_TEST` it throws a message naming the test setups, so a preview started that way passes the schema check in `vite.config.ts` and stops on its first database access. Outside production the client is kept on `globalThis`, so dev server reloads reuse one connection pool.

`pnpm db:seed` runs `prisma db seed`, which runs the `migrations.seed` command from `prisma.config.ts`: `tsx prisma/seed.ts`. Plain Node cannot run it, because the seed imports `#/server/db`, which imports `#/env` and the generated client without file extensions, and Node adds none when it resolves subpath imports. `prisma/seed.ts` loads `.env` before importing anything that validates it, then calls `seed()` from `src/server/seed.ts`. The seed owns the projects with keys TOK and DEMO. In one transaction it deletes their tasks, then the projects (deleting a project first could reach a status while tasks still point at it, which the `RESTRICT` key refuses), and creates both again with statuses, labels, about 30 tasks, subtasks, comments, and activity. Re-running it leaves the same data, and other projects are not touched. The transaction has a 60 second timeout instead of Prisma's 5 second default. `seed()` takes a `now` option for the dates, and accepts a transaction client as well as a `PrismaClient`.

`vitest.config.ts` loads `.env` the same way, for the optional variables; the tests run without a `.env`. The Vitest global setup (`src/test/global-setup.ts`) and `tests/e2e/serve.ts` call `prepareTestDatabase` in `src/test/prepare-test-database.ts`. It starts a PostgreSQL container with `@testcontainers/postgresql`, from the `postgres:<n>` image of the compose `db` service (a registry prefix is allowed; other services are ignored), with a database named `todo_over_kill_<random>` and a random password, since Testcontainers cannot limit the published port to loopback, and runs `prisma migrate deploy` with `DATABASE_URL` set to the container's URL. It returns the URL and a `stop` function, and stops the container itself if the migration fails. It stops with a message when Docker cannot be reached or `docker-compose.yml` has no such image line. Each run has its own container on a port Docker picks, so runs in several worktrees do not share data. Testcontainers' Ryuk reaper stays enabled: it removes the container when the process that started it dies without stopping it.

The global setup runs in the main process, so it passes the URL to the workers with `project.provide('testDatabaseUrl', url)`. `src/test/setup-database-url.ts`, the first setup file of the server project, reads it with `inject` and sets `DATABASE_URL_TEST` and `DATABASE_URL` in `process.env` before any test file imports `src/env.ts`. `src/server/db.test.ts` checks that the client is connected to that container's database.

The CI workflow in `.github/workflows/ci.yml` runs one job with no database service: the unit and e2e runs start their containers on the runner's Docker. It runs `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm test:e2e`, and uploads the Playwright report.
